# Normalization vs Denormalization Tradeoffs
## What
Normalization and denormalization are two fundamental concepts in database management systems (DBMS) that impact the design and performance of databases. Normalization involves organizing data into tables to minimize data redundancy and dependency, while denormalization involves intentionally allowing data redundancy to improve read performance.

## Why
The tradeoff between normalization and denormalization is crucial because it affects the balance between data consistency and query performance. Normalization helps maintain data integrity by reducing data redundancy, but it can lead to slower query performance due to the need for joins. Denormalization, on the other hand, can improve query performance by reducing the need for joins, but it can lead to data inconsistencies and increased storage requirements.

## How
To determine whether to use normalization or denormalization, DBMS designers must consider the specific requirements of their application. They must weigh the need for data consistency against the need for query performance. In general, normalization is preferred for transactional systems that require high data consistency, while denormalization is preferred for analytical systems that require high query performance.

## One exercise or command
To illustrate the tradeoff, consider a simple example of a customer database. A normalized design might have separate tables for customers and orders, while a denormalized design might have a single table that includes customer and order information. The following SQL command creates a denormalized customer table:
```sql
CREATE TABLE customers (
  customer_id INT,
  name VARCHAR(255),
  email VARCHAR(255),
  order_total DECIMAL(10, 2)
);
```

## Senior interview checkpoint

**Prompt:** Choose indexes for a high-cardinality filter + sort query and justify tradeoffs.

**What a senior answer should include**

- Constraints first (traffic, latency, reliability, ownership boundaries).
- Tradeoffs with at least two viable alternatives.
- Failure modes, observability signals, and rollback plan.
- A measurable success criterion after rollout.
