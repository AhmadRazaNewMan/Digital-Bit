# Transaction Isolation Anomalies
## What
Transaction isolation anomalies occur when multiple transactions access shared data simultaneously, leading to inconsistent results. Two common anomalies are dirty read and phantom read. A dirty read happens when a transaction reads uncommitted data from another transaction, while a phantom read occurs when a transaction sees new data inserted by another transaction that was not present when the first transaction started.

## Why
Understanding transaction isolation anomalies is crucial in database management systems (DBMS) because they can lead to data inconsistencies and errors. For instance, in a banking system, a dirty read can result in incorrect account balances, while a phantom read can cause incorrect transaction processing.

## How
To prevent or mitigate transaction isolation anomalies, DBMS use various isolation levels, such as:
* READ UNCOMMITTED: allows dirty reads
* READ COMMITTED: prevents dirty reads but allows phantom reads
* REPEATABLE READ: prevents dirty reads and phantom reads but may cause deadlock
* SERIALIZABLE: prevents all anomalies but can have significant performance overhead

## One exercise or command
To demonstrate a dirty read, consider the following example:
Suppose we have two transactions, T1 and T2, accessing a table `accounts` with columns `id` and `balance`.
T1: `SELECT balance FROM accounts WHERE id = 1;` (reads balance = 100)
T2: `UPDATE accounts SET balance = 200 WHERE id = 1;` (updates balance to 200, but not committed)
T1: `SELECT balance FROM accounts WHERE id = 1;` (reads balance = 200, which is uncommitted data)
