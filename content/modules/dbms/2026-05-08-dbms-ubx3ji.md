# Normalization vs Denormalization Tradeoffs
## What
Normalization and denormalization are two database design techniques used to optimize data storage and retrieval. Normalization involves organizing data into tables to minimize data redundancy and dependency, while denormalization involves intentionally duplicating data to improve query performance.

## Why
The tradeoff between normalization and denormalization lies in the balance between data consistency and query performance. Normalization helps to eliminate data anomalies and improve data integrity, but can result in slower query performance due to the need to join multiple tables. Denormalization, on the other hand, can improve query performance by reducing the number of joins required, but can lead to data inconsistencies and increased storage requirements.

## How
To determine whether to use normalization or denormalization, consider the following factors:
* Data complexity: Normalization is suitable for complex data with many relationships, while denormalization is suitable for simple data with few relationships.
* Query patterns: Denormalization is suitable for queries that require frequent access to related data, while normalization is suitable for queries that require infrequent access to related data.
* Data volume: Denormalization is suitable for large datasets, while normalization is suitable for small datasets.

## One exercise or command
To illustrate the tradeoff between normalization and denormalization, consider a simple example: a database that stores customer information and order history. A normalized database design would separate customer information and order history into two separate tables, while a denormalized design would combine the two tables into a single table. The command to create a normalized database design would be:
```sql
CREATE TABLE customers (
  customer_id INT PRIMARY KEY,
  name VARCHAR(255),
  address VARCHAR(255)
);

CREATE TABLE orders (
  order_id INT PRIMARY KEY,
  customer_id INT,
  order_date DATE,
  FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
```
In contrast, the command to create a denormalized database design would be:
```sql
CREATE TABLE customer_orders (
  customer_id INT,
  name VARCHAR(255),
  address VARCHAR(255),
  order_id INT,
  order_date DATE
);
```

## Senior interview checkpoint

**Prompt:** Choose indexes for a high-cardinality filter + sort query and justify tradeoffs.

**What a senior answer should include**

- Constraints first (traffic, latency, reliability, ownership boundaries).
- Tradeoffs with at least two viable alternatives.
- Failure modes, observability signals, and rollback plan.
- A measurable success criterion after rollout.
