# Transaction Isolation Anomalies
## What
Transaction isolation anomalies refer to the problems that can occur when multiple transactions are executed concurrently in a database management system (DBMS). These anomalies can lead to inconsistent or unexpected results, compromising the reliability and integrity of the data. Two common types of transaction isolation anomalies are dirty read and phantom read.

## Why
Dirty read and phantom read anomalies occur due to the way transactions interact with each other and the database. A dirty read happens when a transaction reads data that has been modified by another transaction, but not yet committed. If the modifying transaction rolls back, the data read by the first transaction becomes invalid. A phantom read occurs when a transaction executes a query, and then another transaction inserts or deletes data that would have been included in the query results, had it been executed again.

## How
To prevent or mitigate these anomalies, DBMSs use various transaction isolation levels, which define the degree to which transactions are isolated from each other. The isolation levels include:
* READ UNCOMMITTED: allows dirty reads
* READ COMMITTED: prevents dirty reads, but allows phantom reads
* REPEATABLE READ: prevents dirty reads and phantom reads, but may still allow non-repeatable reads
* SERIALIZABLE: ensures that transactions are executed in a way that appears to be serial, preventing all types of isolation anomalies

## One exercise or command
To demonstrate the concept of dirty read, consider the following example: 
Suppose we have two transactions, T1 and T2, executing concurrently. T1 updates a row in a table, but does not commit. T2 then reads the updated row. If T1 rolls back, T2 has performed a dirty read.

## Senior interview checkpoint

**Prompt:** Explain how isolation level affects deadlocks in write-heavy workloads.

**What a senior answer should include**

- Constraints first (traffic, latency, reliability, ownership boundaries).
- Tradeoffs with at least two viable alternatives.
- Failure modes, observability signals, and rollback plan.
- A measurable success criterion after rollout.
