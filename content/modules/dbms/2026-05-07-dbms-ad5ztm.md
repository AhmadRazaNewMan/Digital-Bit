# Normalization vs Denormalization Tradeoffs
## What
Normalization and denormalization are two database design approaches that serve different purposes. Normalization involves organizing data in a database to minimize data redundancy and improve data integrity, typically following rules such as First Normal Form (1NF), Second Normal Form (2NF), and Third Normal Form (3NF). On the other hand, denormalization intentionally duplicates data to improve read performance, often used in scenarios where data is mostly read and rarely updated.

## Why
The tradeoff between normalization and denormalization lies in their impact on data consistency, storage space, and query performance. Normalized databases are more resistant to data anomalies and require less storage space but may lead to slower query performance due to the need for joins. Denormalized databases can offer faster query performance but at the cost of increased storage space and potential data inconsistencies.

## How
To decide between normalization and denormalization, consider the specific requirements of your application. For transactional systems where data updates are frequent, normalization is typically preferred to maintain data integrity. For analytical systems where data is mostly read and performance is critical, denormalization might be more suitable. It's also common to use a combination of both, where some parts of the database are normalized for transactional data, and others are denormalized for reporting or analytical purposes.

## One Exercise or Command
An example command to create a normalized table in SQL, following the 3NF rule, could look like this:
```sql
CREATE TABLE Customers (
  CustomerID INT PRIMARY KEY,
  Name VARCHAR(255),
  Email VARCHAR(255)
);

CREATE TABLE Orders (
  OrderID INT PRIMARY KEY,
  CustomerID INT,
  OrderDate DATE,
  FOREIGN KEY (CustomerID) REFERENCES Customers(CustomerID)
);
```
This design separates customer information from order information, reducing data redundancy.
