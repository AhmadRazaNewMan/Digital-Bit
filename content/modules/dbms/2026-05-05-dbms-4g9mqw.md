# Transaction Isolation Anomalies
## What
Transaction isolation anomalies occur when multiple transactions access shared data simultaneously, resulting in inconsistent or unexpected behavior. Two common anomalies are dirty read and phantom read. A dirty read occurs when a transaction reads uncommitted data from another transaction, while a phantom read occurs when a transaction sees new data inserted by another transaction that was not present when the first transaction started.

## Why
Understanding transaction isolation anomalies is crucial in database management systems (DBMS) because they can lead to data inconsistencies and errors. For instance, if a transaction reads dirty data, it may make decisions based on incorrect information, leading to incorrect results. Similarly, phantom reads can cause transactions to miss new data that was inserted after they started, resulting in incomplete or inaccurate results.

## How
To avoid transaction isolation anomalies, DBMS use various isolation levels, such as READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, and SERIALIZABLE. Each level provides a different level of protection against dirty reads and phantom reads. For example, the READ COMMITTED level prevents dirty reads by only allowing transactions to read committed data, while the REPEATABLE READ level prevents both dirty reads and phantom reads by ensuring that transactions see a consistent view of the data for the duration of the transaction.

## One exercise or command
To demonstrate the concept of dirty reads, consider the following example:
- Start two transactions, T1 and T2.
- In T1, update a row in a table and do not commit.
- In T2, read the updated row. If T2 can read the updated row, it is a dirty read.
- To prevent dirty reads, set the isolation level to READ COMMITTED in T2 before reading the row.
