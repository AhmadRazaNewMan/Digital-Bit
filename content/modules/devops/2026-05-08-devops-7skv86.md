# Immutable Artifacts vs Mutable Servers
## What
Immutable artifacts refer to software components or packages that cannot be modified once they are created. This approach is often used in conjunction with containerization and orchestration tools to ensure consistency and reliability in deployments. On the other hand, mutable servers are traditional servers that can be modified after deployment, which can lead to configuration drift and inconsistencies.

## Why
The use of immutable artifacts is preferred over mutable servers because it provides several benefits, including improved security, easier rollbacks, and reduced downtime. With immutable artifacts, any changes to the software or configuration require a new artifact to be created, which can then be deployed to replace the existing one. This approach eliminates the risk of configuration drift and makes it easier to track changes and debug issues.

## How
To implement immutable artifacts, developers can use containerization tools like Docker to package their applications into containers. These containers can then be orchestrated using tools like Kubernetes to manage deployments and scaling. When changes are made to the application or configuration, a new container image is created, which can then be deployed to replace the existing one.

## One exercise or command
To demonstrate the concept of immutable artifacts, you can try creating a Docker image for a simple web application, and then use Kubernetes to deploy it. For example, you can use the following command to create a Docker image: `docker build -t my-web-app .`

## Further reading
* Benefits of immutable infrastructure:
  * Improved security through reduced attack surface
  * Easier rollbacks and debugging
  * Reduced downtime and improved reliability
* Tools for implementing immutable artifacts:
  * Docker for containerization
  * Kubernetes for orchestration
  * Terraform for infrastructure as code
* Best practices for immutable artifacts:
  * Use version control systems to track changes
  * Use automated testing and deployment pipelines
  * Monitor and log deployments for debugging and security purposes

**What a senior answer should include**

- Constraints first (traffic, latency, reliability, ownership boundaries).
- Tradeoffs with at least two viable alternatives.
- Failure modes, observability signals, and rollback plan.
