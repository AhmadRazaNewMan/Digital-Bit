# Immutable Artifacts vs Mutable Servers
## What
Immutable artifacts refer to software components that cannot be changed once they are built and deployed. This approach ensures consistency and reliability across different environments. On the other hand, mutable servers are servers that can be modified after deployment, which can lead to configuration drift and inconsistencies.

## Why
The use of immutable artifacts is essential in DevOps because it eliminates the risk of unintended changes to the system. When servers are mutable, it becomes challenging to maintain a consistent state, and debugging issues can be time-consuming. Immutable artifacts provide a clear audit trail, making it easier to track changes and maintain compliance.

## How
To implement immutable artifacts, organizations can use containerization tools like Docker, which package the application and its dependencies into a single container. This container is then deployed to a server, replacing any existing version. This approach ensures that the application is consistent across different environments.

## One exercise or command
To demonstrate the concept of immutable artifacts, you can create a Docker image for a simple web application and deploy it to a server. The command to build a Docker image is: 
`docker build -t my-web-app .`

## Further reading
* Key benefits of immutable infrastructure:
  * Improved security and compliance
  * Reduced risk of configuration drift
  * Faster debugging and issue resolution
* Tools for implementing immutable artifacts:
  * Docker
  * Kubernetes
  * AWS Elastic Container Service (ECS)
* Best practices for adopting immutable artifacts:
  * Use version control systems to track changes
  * Implement continuous integration and continuous deployment (CI/CD) pipelines
  * Monitor and log application performance and issues

## Senior interview checkpoint

**Prompt:** Design CI guardrails to prevent secret leaks and oversized images.

**What a senior answer should include**

- Constraints first (traffic, latency, reliability, ownership boundaries).
- Tradeoffs with at least two viable alternatives.
- Failure modes, observability signals, and rollback plan.
- A measurable success criterion after rollout.
